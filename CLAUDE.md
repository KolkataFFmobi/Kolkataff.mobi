# CLAUDE.md — kolkataff.mobi

This is a pure static informational site publishing Kolkata Fatafat results, built by a single dependency-free Node build script.

## Hard prohibitions

- NO tips, predictions, lucky numbers, "ghosh babu tips", or any content suggesting what numbers to play — not on any page, not in FAQ answers, not in meta descriptions. Permanent content policy.
- NO WordPress, no CMS, no database on public routes, no client-side JS framework on public pages.
- NO third-party JS, with ONE explicit, dated exception: Google Analytics (gtag.js, GA4 property `G-RES0GKZ8FY`), added 2026-07-19 by deliberate user request — see "Analytics exception" below for the exact, narrow scope. Nothing else third-party is permitted. One reserved ad-slot div per page (empty for now, fixed height to prevent CLS); the ad tag is added manually later.
- NO forms anywhere. Contact page shows an email address only.

## Stack lock (do not change)

- Pure static site generated by a single dependency-free Node.js build script (build.js). No frameworks; no npm packages except Node stdlib. If a package seems truly unavoidable, STOP and ask first.
- Source of truth: data/results.json.
- Output: /dist (deployable directly to Cloudflare Pages).
- No external/third-party JS; first-party inline vanilla JS is permitted (≤ 2KB total per page, no frameworks, no fetch/XHR calls). All CSS inline in `<head>`. System font stack only.
- Canonical domain is pinned by ONE constant: `SITE_ORIGIN = "https://kolkataff.mobi"` (non-www, https) in lib/core.js. Every canonical tag, sitemap URL, JSON-LD `url`/`@id`, and og:url derives from it. Never hard-code a host anywhere else.
- Today-table layout is bazi-per-row (columns = Patti | Single | Result) so it fits a 360px viewport with no horizontal scroll. Keep it that way.

## The four-way sync rule (core mechanic — enforced in build.js, never an afterthought)

"Every build triggered by a result update MUST atomically update, from the same timestamp variable:
1. Homepage HTML: the result table cell + visible "Updated: HH:MM IST" for that bazi
2. sitemap.xml: `<lastmod>` on the homepage entry (ISO 8601, +05:30 offset)
3. Homepage JSON-LD: WebPage.dateModified
4. File mtimes in /dist (so the host serves fresh Last-Modified/ETag)
If these can diverge, the build script is wrong. One function produces the timestamp and threads it through all four. A post-build assertion greps the built homepage's dateModified and the sitemap lastmod and fails the build if they don't match."

The visible H1 date, `<title>` date, meta description date, and table caption date all derive from the same `today` variable. A build where any of these disagree is a failed build.

Builds are hermetic: dist/ is emptied at build start and fully regenerated (public/ passthrough is re-copied). Any file in dist/ not derived from the current build is a build failure — enforced by the `[hermetic]` post-build assertion, which checks every dist/ .html against `PAGE_INVENTORY` (the fixed pages) plus the valid dynamic routes (`/old-results/YYYY-MM/`, one per earlier calendar month). There are NO per-day `/result/DD-MM-YYYY/` pages: the archive is rendered INLINE, grouped by month, and `dist/result/` must not exist. Legacy `/result/*` URLs 301-redirect to `/old-results/`.

**The today-result table is the centerpiece component.** At a 360px mobile viewport, the H1, the LIVE badge, and the start of today's result table must be visible without scrolling. Nothing may push it below the fold — this is why the next-result strip is a fixed single line (~48px), not a multi-line block. The ad slot (and everything else that structurally trails the page body) must NEVER sit above the today-result table, or above the page's own `<h1>`, on any page — enforced by the `[centerpiece]` post-build assertion.

**Source order = visual order.** No CSS may reorder content relative to its DOM position: no `order:`, no `flex-direction: *-reverse`, no `position:absolute` used to reposition a visible content block. The one documented exception is the `.visually-hidden` sr-only utility (used to hide a redundant table caption from sighted users while keeping it for screen readers) — it removes an element from the visual layout without moving anything else, so it is not a reordering technique. Enforced by the `[source-order]` post-build assertion; do not add a second exception without updating that assertion's allowlist.

**Overflow safety nets scroll, they never hide.** Any element wide enough to risk exceeding its container (day-grid tables, the date-jump nav, the month-links row) gets its own `overflow-x:auto`, scoped to that element only — never a blanket `overflow-x:hidden` on `html`/`body` as a page-wide catch-all. A blanket hide silently deletes content a user has no way to reach (verified once: it clipped the month-links row's earliest months with zero visual indication anything was missing); a scoped `overflow-x:auto` degrades to a swipeable/scrollable region instead, so nothing is ever unreachable. `document.documentElement.scrollWidth` is not a reliable "is this actually broken" signal on its own — it reports total content extent even for a properly self-contained `overflow:auto` region; the real test is attempting `window.scrollTo()` on the page and confirming `scrollX` doesn't move.

**Every functional block gets its own heading.** The today-result table, the yesterday block, the Last 30 Days section, the timings table, and the FAQ must be immediately preceded by a descriptive `h2` (or the page's own `h1` when the block IS the whole page, e.g. `/faq/`). Utility navs (breadcrumb, pager, date-jump, month-links) don't need one. Archive DAY tables (day-grid component, below) are the one deliberate exception: each day's own date is the table's `<caption>` (the styled, sticky date bar), not a separate external `h2` — adding one back would reintroduce the exact visible date-duplication bug a previous pass fixed.

## Performance budget (build fails if exceeded)

- Homepage HTML ≤ 100KB (raised from 60KB to fit the Last 30 Days archive section, per competitor-consensus UX — see Post-build assertions #4); inline CSS budget is unchanged.
- All CSS inline in `<head>`, ≤ 10KB, system font stack only (no webfonts).
- No external/third-party JS; first-party inline JS ≤ 2KB per page (currently: the homepage next-result countdown). Zero external requests except the future ad tag.
- No images above the fold except inline SVG favicon/logo.
- Ad slot has a fixed height (250px) so CLS is 0.
- Mobile-first; audience is low-end Android; layout must work at 360px width.
- Light theme only (warm off-white bg, near-black text, WCAG AA contrast): users check results on cheap Android screens outdoors/in daylight, so a light background with maximum contrast is an accessibility requirement — do not ship a dark theme.

## Daily freeze behaviour

- `npm run freeze-day -- --date YYYY-MM-DD` marks that day as frozen and rebuilds: the day is then rendered inline in the `/old-results/` archive (paginated by month) and rolls into the homepage's "Yesterday"/"Last 30 Days" blocks, all from the same build. There are no per-day `/result/` pages. Intended to be cron'd at 00:05 IST for the day that just ended.
- `npm run add-result -- --date YYYY-MM-DD --bazi N --patti PPP --single S` validates (patti = 3 digits, single = 1 digit, single must equal the last digit of the sum of the patti digits — reject with an explanation otherwise), writes results.json, and runs a full build.

## CLIs & build

- `npm run build` — full clean build into /dist; runs every post-build assertion (below). Pin "today" for deterministic testing via `KFF_TODAY=YYYY-MM-DD`; production uses the real Asia/Kolkata date.
- `npm run add-result -- ...` / `npm run freeze-day -- ...` — see above.
- `npm run deploy` — build (all assertions) → apply deploy guards (below) → `npx wrangler pages deploy dist`.
- `npm run update -- --date … --bazi … --patti … --single …` — record a result then deploy, in one command (the real 8×/day workflow). If the result is invalid, it does not deploy.
- `npm run serve` — local dependency-free preview of /dist (dev only; not deployed).

## Post-build assertions (build FAILS on any)

These are enforced in build.js `runAssertions` and must never be weakened to make a build pass:
1. **Four-way sync** — homepage JSON-LD `dateModified` == sitemap homepage `<lastmod>` == index.html mtime, all == the single `pageModifiedFor` value.
2. **JSON-LD** — every `application/ld+json` block on every page `JSON.parse`s.
3. **JS discipline** — no external `<script src>` (no third-party JS) except the one documented GA4 `gtag.js` loader (exact URL match only, and it must be present on every emitted page — "every page trackable"); inline first-party JS ≤ 2KB per page and must not use fetch/XHR/WebSocket; `type="application/ld+json"` data blocks are exempt.
4. **Budget** — homepage ≤ 100KB (raised from 60KB for the Last 30 Days archive section, per competitor-consensus UX); inline CSS ≤ 10KB. Since 2026-07-19, build.js strips CSS comments at inline time (`CSS_SHIPPED`) so comments in `lib/css.js` are dev-only again, and the budget assertion measures the SHIPPED bytes; the structural CSS assertions (ad-slot height, source-order, daygrid mechanism) still read the raw source constant.
5. **Canonical domain** — every page has exactly one canonical; the set of canonicals == the set of sitemap `<loc>` entries, 1:1 for the FIXED canonical pages (404 and `/old-results/YYYY-MM/` month-archive pages are excluded from this match — see #18 — but still each carry their own single canonical); every URL under `SITE_ORIGIN`; zero `localhost`, zero insecure/foreign `http://` (XML/SVG namespace URIs excepted), zero `www.` of our own domain; every file valid UTF-8 with no U+FFFD.
6. **Content policy** — case-insensitive scan of all pages for tip/tips/predict*/lucky/"ghosh babu"/"sure number"/"target number". Only the exact disclaimer sentences (or, where the same wording appears with varying trailing punctuation across pages, the exact core *phrase*) in the `POLICY_ALLOW` literal list may contain these words; any other hit fails the build. **If page copy changes, update `POLICY_ALLOW` in lockstep — never loosen the patterns.**
7. **Ad slot** — `.ad-slot` has a fixed 250px height in CSS; at most one ad slot per page.
8. **Lang** — every page `<html lang="en">`; the homepage has at least one `lang="bn"`.
9. **Legacy redirects** — `dist/_redirects` is generated from the `REDIRECT_MAP` constant. Every 301 target must exist in the build; no target may itself be a redirect source (no chains); no target may point to a `DELIBERATELY_DEAD` path (tips/lucky/ghosh-babu/dpboss/main-bazar/siliguri/wp-*/feed/category/author URLs are left to resolve to the 404 page on purpose).
10. **Source order** — no `order:`, no reversed `flex-direction`, no repositioning `position:absolute` in the CSS, outside the documented `.visually-hidden` sr-only exception.
11. **Template consistency** — the `<header class="site-header">…</header>` and `<footer class="site-footer">…</footer>` fragments are checksummed (sha256) across every emitted page; the build fails if any page's header or footer differs by even one byte.
12. **Centerpiece** — the ad slot never appears before the today-result table or before the page's own `<h1>`, on any page.
13. **Old-results permanent components** — every old-results page (the canonical latest-month page and every `/old-results/YYYY-MM/` page) must contain both `class="date-jump"` and `class="month-links"`. These are PERMANENT, protected components — do not remove them in a future pass; the build fails loud if they're missing instead of silently shipping the regression (this happened once already).
14. **Semantic markup** — every page has exactly one `<main>` and exactly one `<h1>`; every `<table>` has a `<caption>`; every `<section>` is a NAMED region (`aria-labelledby` → an existing heading id, or `aria-label` for a heading-less block); ids are unique per page and every `aria-labelledby` resolves to an id that exists on the page. Plus homepage element-choice spot-checks: `<nav aria-label="Main menu">`, `<table id="kolkata-ff-result-today">`, the next-result strip is a `role="status" aria-live="polite"` region with `id="next-result-countdown"`, the "updated" chrome is a `<time datetime>`, and the ad slot carries `aria-label="Advertisement"`.
15. **Compact-table date header** — every day-grid date is a **visible `<caption class="dg-date">`** (never a `<th class="dg-date">`) still carrying the full `"Kolkata Fatafat result {date}"` accessible name, and the CSS mechanism behind the fix is present (`.dg-scroll{container-type:inline-size}` and `.dg-date` is `position:sticky` + `width:100cqw` + `text-align:center`), so the date bar stays centred and fixed during horizontal scroll.
16. **Entity alias frequency** — every term in `content.ENTITY_ALIASES` (Kolkata FF, Kolkata Fatafat, কলকাতা ফটাফট, Kolkata Fatafati, Kolkata Fotafot, Calcutta Fatafat, KolkataFatafat, KFF — 8 total) appears in the DEFINITIONAL_PARA "also known as" sentence **exactly once** (checked against the source string, boundary-aware so "Kolkata Fatafat" never false-matches as a prefix of "Kolkata Fatafati"). If that sentence changes, keep `ENTITY_ALIASES` in lockstep. `GAME_ALT`/`SITE_ALT` (JSON-LD alternateName) carry the same alias set, minus whichever name is already each node's own `name`.
17. **Old-records redirect** — both `/old-records` and `/old-records/` must exist in `_redirects` as 301s to `/old-results/`.
18. **220-Patti membership** — every declared patti in the data must be a member of the computed canonical 220-Patti set (`patti220BySingle()`); catches data typos and generator-convention drift. The generator itself hard-fails if it doesn't produce exactly 220 pattis in 10 groups of 22.
19. **Sitemap + robots audit** (2026-07-19) — `sitemap.xml` contains EXACTLY the fixed canonical page set — homepage + `/old-results/` + every page in `CONTENT_LASTMOD` (12 today; would be 13 once/if `/chart-2026/` is built) — no month-archive pages, no anchors, no legacy/asset URLs, trailing-slash form. Every `<loc>` resolves to a real emitted page whose own canonical equals that `<loc>` exactly. `<lastmod>` is never build time for anything except the homepage (which legitimately uses it as a fallback only when no bazi has been declared yet today): `/old-results/` uses `lastArchiveChange()` (the latest real `declaredAt` across all frozen days), and every other static page uses its `CONTENT_LASTMOD` entry — **bump that date by hand when you actually edit that page's title/description/H1/body copy**; a bare rebuild with no content change must reproduce byte-identical `lastmod` values (verified: two builds a few seconds apart produced an identical sitemap except the homepage's own line). `robots.txt` is asserted to allow all crawling with exactly one `Sitemap:` line, no `Disallow`, no `Crawl-delay`.

## Automated result updates (scripts/auto-update.js + .github/workflows/auto-update.yml, added 2026-07-21)

`npm run auto-update` (or `-- --dry-run`) polls the public source sites, ingests confirmed results, freezes finished days, and rebuilds — the unattended counterpart of add-result/freeze-day, cron'd via GitHub Actions (every 15 min through the IST result day + a 00:05 IST freeze pass) so it runs while humans sleep. Sources: kolkataff.tv (dated `<h3>DD/MM/YYYY</h3>` tables, patti+single) and kolkataresultff.com (dated month-record tables, patti only — single derived). playpro.in is JS-rendered and NOT scrapeable server-side. Its SAFETY RULES are earned, not decorative — do not weaken: (1) dated history tables only, never a source's "today" widget (kolkataff.tv's rolls to tomorrow early); (2) ≥2-source patti agreement before publishing (kolkataff.tv carried a wrong bazi-8 for days once); (3) time-gate — no bazi ingested before its scheduled IST slot passes; (4) digit-sum validation; (5) a mismatch against an already-published result is a CONFLICT (exit 2, CI notifies) and is NEVER auto-overwritten. The CI workflow commits data changes but deploys ONLY when `SCHEDULE_VERIFIED` is true and `dist/.dummy-data` is absent — the exact scripts/deploy.js guards, re-enforced in YAML. Setup steps for the repo/secrets live in SETUP-AUTOMATION.md (repo doc, not a site page).

## Platform (Cloudflare dashboard) launch config — NOT expressible in this repo

`_redirects` on Cloudflare Pages matches PATHS only; host-level redirects live in the zone config and cannot be asserted by the build. Required before/at launch (verify in the dashboard):
- **Always Use HTTPS** on for the zone (http → https).
- **www → apex**: `www.kolkataff.mobi/*` 301 → `https://kolkataff.mobi/<path>` (redirect rule + proxied DNS record for `www`).
- **fatafat subdomain → apex** (requested 2026-07-19): proxied `AAAA fatafat 100::` DNS record + redirect rule — hostname equals `fatafat.kolkataff.mobi` → dynamic 301 to `concat("https://kolkataff.mobi", http.request.uri.path)`, preserve query string. Path-preserving on purpose so legacy deep links chain into `_redirects`.

## Deploy guards (deploy.js refuses, non-zero exit, when)

- The build fails any assertion.
- `dist/.dummy-data` exists — stamped whenever data/results.json still carries the `_note` DUMMY marker. Never deploy dummy results; replace with real data and remove `_note`.
- `lib/core.js SCHEDULE_VERIFIED` is false — the bazi times are UNVERIFIED SEED DATA. Flip to true MANUALLY only after verifying against authoritative live sources; do not change the seed times when flipping it.

- **Interactive-element polish** (2026-07-19): `.month-links .cur` (the current-month pill) now shares its box model (padding/border/border-radius) with `.month-links a` via a combined selector — previously it was a bare `<span>` with only background/color set, so it rendered as a sharp-cornered box with text flush to the edges next to the properly-padded rounded pills, which is what "inconsistent nav" / "ugly" was about. Site-wide, `a,button` also got `-webkit-tap-highlight-color:transparent` (kills the default blue/grey mobile tap-flash) and a shared `:focus-visible` outline (`--accent-dark`, keyboard-only in most browsers — a programmatic `.focus()` call in automated testing does not reliably trigger it, that's expected, not a bug). If a future component adds its own pill/button style, give it the same box-model treatment on ALL its state variants (default, current/active, hover) from the start rather than adding one variant at a time.

## Analytics exception (deliberate, narrow — added 2026-07-19)

CLAUDE.md's "no third-party JS" rule has exactly ONE carved-out exception: Google Analytics (gtag.js), GA4 property `G-RES0GKZ8FY`, added by explicit user request. The scope is intentionally narrow — do not widen it without the same explicit process:

- Exactly one external `<script src>` is permitted: the `gtag.js` loader for this one measurement ID. build.js's `[js]` assertion allows only an EXACT match on that URL and asserts it is `async`; any other external script still fails the build. The assertion also requires the loader on every emitted page, enforcing "every page is trackable."
- The tiny first-party `dataLayer`/`gtag('config', ...)` snippet still counts against the existing ≤2KB inline-JS-per-page budget and must not itself use fetch/XHR (it doesn't — it only calls `dataLayer.push`).
- Both are injected once, in the shared `layout()` function in build.js (`ANALYTICS_SNIPPET`, placed first in `<head>` per Google's own guidance) — there is exactly one place this can drift.
- `dist/_headers` CSP was loosened ONLY for the Google Analytics hosts this needs: `script-src` gains `https://www.googletagmanager.com`; `connect-src` AND `img-src` both use the `https://*.google-analytics.com` wildcard (img-src too because gtag falls back to image-tag transport on devices without sendBeacon/fetch — this audience — and those hits can go to regional hosts like `region1.google-analytics.com`). `connect-src` also carries `'self'` (same-origin only; inline JS is build-asserted to never fetch, so it opens nothing in practice, but it stops strict-CSP tooling like Lighthouse's in-page robots.txt fetch from reporting false failures). Nothing else is opened.
- **Dev-server caveat**: `scripts/serve.js` re-reads `_headers` on every request and gzips text responses — both deliberate, so local audits see the same CSP and compression behaviour production (Cloudflare) has. A stale header cache here once made local Lighthouse report gtag as CSP-blocked when production would have been fine.
- Privacy Policy and Cookie Policy copy (`lib/content.js`) were updated to disclose the actual GA4 usage — they previously said no tracking was active, which would now be false.
- When the ad tag lands later (see the CSP tradeoff above), it gets the same treatment: an explicit, narrow, documented CSP + assertion carve-out, never a blanket relaxation.

## Guiding principle

Fix root causes, not symptoms — no guards/retries papering over a broken update pipeline.
